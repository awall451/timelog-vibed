# Hosted demo — plan and notes

Status: **planning** (2026-08-17). Nothing here is implemented yet; this file stages the design so it survives context loss.

## Hosting: Azure Static Web Apps (Free)

The demo build (`npm run build:demo`, `VITE_DEMO_MODE=true`) is pure static output — `adapter-static`, SSR off, `sql.js` WASM in the browser, no API. It does not need a VM or a container at runtime. Target:

- **Azure Static Web Apps, Free tier** — `swa-sigilworks-timelog`, resource group `rg-sigilworks-site` (eastus2). $0/mo.
- **Custom domain:** `timelog.sigilworks.dev` (Cloudflare CNAME, DNS-only, SWA managed cert).
- **CI/CD:** Azure DevOps Pipelines, source = this GitHub repo (code stays on GitHub). Pipeline definition lives at `azure-pipelines.yml` in this repo. Stages mirror the sigilworks.dev site pipeline: TEST → SCAN (trivy, CRITICAL gate) → GREEN (SWA `green` environment + smoke test + review link) → PROMOTE (manual approval → production + smoke test).
- **Build artifact:** the existing `frontend/Dockerfile.demo` builder stage produces `build/`; the pipeline extracts that directory from the image and hands it to `AzureStaticWebApp@0` with `skip_app_build: true`. The nginx stage is only used for local hosting and for trivy image scanning.
- **`staticwebapp.config.json`** replaces `nginx.demo.conf` in production: SPA fallback (`navigationFallback` → `/index.html`), long cache for `/_app/immutable/*`, security headers. Lives in `frontend/static/` so it ships inside `build/`.

`docker-compose.demo.yml` / `nginx.demo.conf` stay for local runs.

## Planned code change: calendar-anchored date rotation

Problem: the seed DB is a fixed snapshot (2025-12-02 → 2026-04-22). Every day it ages, the dashboard "Today"/"Yesterday" views empty out and the heatmap goes stale.

Design (not yet implemented):

1. **Seed = one full year of entries.** Generated by a deterministic script (`scripts/gen-demo-seed.py`, seeded RNG) that reads the real `data/timelog.db`, keeps its project/category vocabulary, hours distribution and weekday pattern, and tiles/jitters it into 365 days. Must never emit `02-29`. Output: `frontend/seed/timelog.db` (tracked). Reproducible from a fresh checkout.
2. **Re-year at load time** in `frontend/src/lib/demo/db.ts` `load()`, applied to both the fresh-seed and IndexedDB-hydrated paths:

   ```
   year(row) = (MM-DD of row <= MM-DD of today) ? thisYear : thisYear - 1
   ```

   Every row lands in the trailing 365-day window ending today. Jan 15 is always Jan 15, every year. Idempotent and stateless — no anchor/offset bookkeeping. Visitor-added entries are re-yeared too (harmless).

   ```sql
   UPDATE entries SET date =
     CASE WHEN strftime('%m-%d', date) <= :todayMMDD
          THEN :thisYear || substr(date, 5)
          ELSE :lastYear || substr(date, 5) END;
   ```
3. **`api.entries.last`** in `frontend/src/lib/demo/api.ts` must order by `date DESC, id DESC` (highest id is no longer the latest date after re-yearing).

Known trade-off: same MM-DD → weekday shifts by one each year, so weekend cells occasionally light up on the heatmap. Accepted. (Alternative: rotate by 364 days to keep weekdays perfect at the cost of calendar drift.)

Why not a server-side cron: visitors keep their own IndexedDB copy and never re-fetch the seed, so only a client-side transform reaches returning visitors. Also: no server.
